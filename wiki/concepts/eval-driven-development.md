## 概要
**eval-driven development** は「エージェントが実現できるようになる**前に**、計画中の能力を定義する eval を作り、そこへ向けて反復する」開発様式。Anthropic はこれを推奨実践として明示し、ゼロから信頼できる eval へ至る道筋を **Step 0〜8** のロードマップとして提示している(出典: Anthropic, 2026-01-09)。

> 社内では「今日は "そこそこ" 動くが、数か月後のモデルにベットした機能」を作ることが多い。低い pass 率から始まる capability eval がその賭けを可視化し、新モデルが出たとき suite を回せばどのベットが当たったかがすぐ分かる。→ [[capability-vs-regression-evals]]

[[spec-driven-development]] が「自然言語仕様を第一級成果物にする」のと同型の運動で、eval-driven development は**実行可能な受け入れ基準としての eval** を第一級成果物にする。記事も「eval task を定義することは、プロダクト要件が着手できるほど具体的かをストレステストする最良の方法の一つ」と述べる。

## Step 0〜8

### 初期データセットの収集

**Step 0. 早く始める**
数百 task が必要だと思い込んで着手が遅れるチームが多いが、実際は**実際の失敗から取った 20〜50 の単純な task で十分な出発点**になる。開発初期はシステムへの各変更の効果が明白で大きいため、小さいサンプルサイズで足りる。成熟したエージェントほど小さな効果を検出するために大きく難しい eval が要るが、初期は 80/20 でよい。
**待つほど eval は作りにくくなる**: 初期はプロダクト要件がそのままテストケースに翻訳できるが、遅れると稼働中のシステムから成功基準をリバースエンジニアリングする羽目になる。

**Step 1. 既に手動でやっているテストから始める**
開発中に回している手動チェック——リリース前に確認する挙動、エンドユーザーがよく試す task——から始める。既に本番稼働しているならバグトラッカーとサポートキューを見る。**ユーザー報告の失敗をテストケース化**すれば suite が実使用を反映し、ユーザー影響で優先度を付ければ労力が効く場所に投資できる。

**Step 2. 曖昧さのない task を、リファレンス解つきで書く**
task の質を上げるのは見た目より難しい。
- 良い task の判定基準: **2人のドメイン専門家が独立に同じ pass/fail 判定に至る**か。彼ら自身がその task を解けるか。解けないなら task を練り直す。
- **task 仕様の曖昧さは、そのまま指標のノイズになる**。model-based grader の基準にも同じことが言える(曖昧な rubric は一貫しない判定を生む)。
- 各 task は**指示を正しく守るエージェントなら通せる**ものであること。これは微妙な話で、Terminal-Bench の監査では「スクリプトを書け」と言いながらパスを指定していない task で、テスト側が特定パスを前提にしていたため、エージェントに非がないのに落ちる事例が見つかった。**grader が見るものはすべて task 記述から明らかであるべき**。
- frontier モデルで**多数 trial にわたる 0% pass(0% pass@100)は、能力不足でなく task が壊れている signal** → [[pass-at-k]]。
- **リファレンス解**(全 grader を通す既知の動作解)を task ごとに作る。task が解けることの証明であり、grader が正しく構成されていることの検証にもなる。

**Step 3. バランスの取れた問題セットを作る**
ある挙動が**起きるべきケースと起きるべきでないケースの両方**をテストする。片側だけの eval は片側だけの最適化を生む(検索すべきときに検索するかだけを見れば、ほぼ何にでも検索するエージェントができあがる)。**クラス不均衡**な eval を避ける。
- 事例: Claude.ai のウェブ検索 eval。難しかったのは「検索すべきでないときに検索させない」ことを、「適切なときには広範なリサーチをする」能力を保ったまま実現すること。チームは**両方向**をカバーする eval を作った——検索すべきクエリ(天気を調べる)と、既存知識から答えるべきクエリ(「Apple の創業者は?」)。**undertriggering(すべき時にしない)と overtriggering(すべきでない時にする)のバランス**を取るのは難しく、prompt と eval の双方に何度も改良が要った。以後も例が出るたび eval に追加してカバレッジを広げている。

### harness と grader の設計

**Step 4. 安定した環境を持つ堅牢な eval harness を作る**
- eval 内のエージェントが**本番のエージェントとほぼ同じように機能する**こと、そして**環境自体が追加のノイズを持ち込まない**ことが本質的。
- **各 trial はクリーンな環境から始めて「隔離」する**。不要な共有状態(残存ファイル、キャッシュ、リソース枯渇)は、エージェント性能ではなくインフラの不安定さによる**相関した失敗**を生む。
- **共有状態は性能を人為的に押し上げることもある**: 社内 eval で Claude が**前の trial の git 履歴を調べて**一部 task で不当な優位を得ていたのを観測した。
- 複数の別々の trial が同じ環境上の制限(CPU メモリ不足など)で落ちるなら、それらの trial は同じ要因に影響されており**独立ではない**。eval 結果はエージェント性能の測定として信頼できなくなる。

**Step 5. grader を注意深く設計する**
決定論的を優先、必要なとき/柔軟性のために LLM、追加検証に人間を慎重に。**経路ではなく成果物を採点する**、**部分点**、**LLM judge のキャリブレーションと "Unknown" の逃げ道と次元ごとの分離**、**ハック耐性**。詳細は [[graders]] に分離。

### 長期の維持と活用

**Step 6. transcript を読む**
- 多数の trial の transcript と採点を読まない限り、grader がうまく働いているかは分からない。**Anthropic は eval transcript 閲覧のツールに投資し、定期的に時間を取って読んでいる**。
- task が落ちたとき、transcript が「エージェントが本当に間違えたのか、grader が妥当な解を却下したのか」を教える。エージェントと eval の挙動に関する鍵となる詳細もしばしば浮かび上がる。
- **失敗は公平に見えるべき**: 何を間違えたのか、なぜかが明白であること。スコアが伸びないとき、それがエージェント性能のせいで eval のせいではないと確信できる必要がある。
- transcript を読むことは、**eval が本当に重要なことを測っているかを検証する手段**であり、エージェント開発の決定的なスキル。

**Step 7. capability eval の飽和を監視する**
100% の eval は回帰を追跡するが改善の signal を与えない。→ [[capability-vs-regression-evals]]
規範として、**誰かが eval の詳細を掘り下げ transcript をいくつか読むまで、eval スコアを額面どおりに受け取らない**。採点が不公平・task が曖昧・妥当な解が罰せられる・harness がモデルを制約している、のいずれかなら eval を改訂する。

**Step 8. オープンな貢献と保守で suite を長期的に健全に保つ**
- eval suite は**生きた artifact**であり、有用であり続けるには継続的な注意と明確なオーナーシップが要る。
- Anthropic が試して最も効果的だったのは、**専任の evals チームが中核インフラを持ち、ドメイン専門家とプロダクトチームが eval task の大半を貢献し自ら評価を実行する**形。
- AI プロダクトチームにとって、eval の所有と反復は**ユニットテストの保守と同じくらい日常的**であるべき。初期テストでは「動く」が、明文化されていない期待に応えられない AI 機能に何週間も浪費しうる——よく設計された eval なら早期に表面化させられた期待に。
- **プロダクト要件とユーザーに最も近い人が成功を定義するのに最適**。現在のモデル能力なら、プロダクトマネージャー・カスタマーサクセス・セールスが Claude Code を使って eval task を PR として貢献できる。**やらせるべきで、さらに言えば積極的に可能にすべき**。

## まとめ(記事の結論)
eval のないチームは反応的ループにはまり、1つの失敗を直しては別を生み、真の回帰とノイズを区別できない。早期に投資したチームでは逆のことが起きる——**失敗がテストケースになり、テストケースが回帰を防ぎ、指標が当て推量を置き換えることで開発が加速する**。eval はチーム全体に登るべき明確な丘を与え、「エージェントが悪くなった気がする」を行動可能なものに変える。価値は複利で効くが、それは eval を後付けでなく**中核コンポーネント**として扱った場合に限る。

パターンはエージェント種別で変わるが基本は不変:
1. **早く始める**。完璧な suite を待たない。
2. 見えている失敗から**現実的な task を仕入れる**。
3. **曖昧さのない堅牢な成功基準**を定義する。
4. **grader を注意深く設計し、複数種を組み合わせる**。
5. 問題が**モデルにとって十分難しい**ことを確認する。
6. **S/N 比を上げるために eval を反復する**。
7. **transcript を読め!**

> AI エージェント評価はまだ黎明期で急速に進化している分野。エージェントがより長い task を担い、マルチエージェントで協調し、より主観的な仕事を扱うようになれば、手法も適応が要る(記事の締め)。
